Quick heads-up before I touch the code: those two model names are real, but they're not drop-in replacements for the OpenAI calls in your script.

- **`gemini-3.5-transcribe-live`** is a *streaming* model — it works over a WebSocket (Google's Live API), sending audio continuously and getting back interim/final transcript events. Your script currently does the opposite: VAD buffers a whole utterance, then sends one finished WAV file for a single request/response.
- **`gemini-3.5-live-translate-preview`** is *speech-to-speech* — audio in, translated audio out (over the same Live API/WebSocket). It doesn't take English text and return Spanish text like `gpt-4.1-mini` does. It also produces the transcript as a side output, so it could actually replace steps 3+4 of your pipeline entirely, not just step 4.

So there are two very different ways to do this migration:

1. **Minimal-change version** — keep your existing VAD-then-batch architecture, but use Gemini's *non-streaming* equivalents instead: `gemini-3.5-transcribe` for STT on each utterance WAV, and a regular Gemini text model (e.g. `gemini-3-flash`) for the EN→ES text translation. Same script shape, same logic, just swapped API calls.
2. **True real-time rewrite** — drop the VAD/batching entirely and stream mic audio straight into `gemini-3.5-live-translate-preview` over a WebSocket; it does English→Spanish speech-to-speech in one continuous session, and you pull the EN and ES transcripts out of the response stream to write to your file. This is closer to what those exact model names are built for, but it's a materially different, async-based script.
