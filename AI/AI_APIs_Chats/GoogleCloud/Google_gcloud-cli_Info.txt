📦 3. Cloud Storage Management (gcloud storage, 5 GiB free)
**Things to keep in mind**
    - **Maps vs. data:** interactive maps (geemap/folium) can't be sent to a bucket. Export rasters with `Export.image.toCloudStorage` and vector data with `Export.table.toCloudStorage`. You can render maps from those files afterward.

    - **Service accounts:** if you run scripts non-interactively, the service account must be registered for Earth Engine, have `earthengine.writer`, and have bucket access

    - **Verify:** `gcloud storage ls gs://ag-remote-bucket01/exports/` shows whether the files landed.

Setup
--------
**1. Enable the APIs**
$ gcloud services enable earthengine.googleapis.com storage.googleapis.com --project=agremotesensing

**2. Grant roles on the project**
Owners already have these. For a Service Account, grant:

$ gcloud projects add-iam-policy-binding agremotesensing \
  --member="user:marron.bruce.mx@gmail.com" \
  --role="roles/earthengine.writer"

$ gcloud projects add-iam-policy-binding agremotesensing \
  --member="user:marron.bruce.mx@gmail.com" \
  --role="roles/serviceusage.serviceUsageConsumer"

**3. Grant write access on the bucket (the usual culprit for failed exports)**
Exports write to the bucket as whoever is authenticated, so that identity needs object permissions on `ag-remote-bucket01`:

$ gcloud storage buckets add-iam-policy-binding gs://ag-remote-bucket01 \
  --member="user:marron.bruce.mx@gmail.com" \
  --role="roles/storage.objectAdmin"

  --flatten="bindings[].members" \

 ############################
 google-cloud-cli (gcloud) vs
 Service Account (.json credential file)
 #############################
When you run a Python script using a .json credential file to call earthengine-api, you are entirely bypassing the google-cloud-cli (gcloud) for that runtime. Your code communicates directly with the Earth Engine servers via an embedded Python library (google-auth), without looking at or needing your terminal's gcloud installation.
The programmatic link between your code, the JSON file, and the CLI exists through the underlying Google Identity and Access Management (IAM) framework.

🔑 1. The Shared Link: The Service Account Identity
The .json file you are using is a Service Account Key.
• That Service Account belongs to a Google Cloud Project.
• If you install and use the google-cloud-cli, you are acting as a Human User (an email account).
• Your human account and your Python script's service account are two separate "actors" knocking on the same door (the GCP Project).


💡 The Takeaway
Your script doesn't depend on the CLI because your .json file contains its own built-in authentication tokens. The CLI is just a tool you can choose to log into with that same file if you ever need to perform manual system administration tasks (like inspecting Cloud Storage buckets or creating sub-folders) through your terminal

me:
so I can leave my .json file Service Account credentials in place in Python scripts and just use gcloud cli for general tasks in Google Cloud?

Google:
Yes, absolutely. You can leave your Python scripts exactly as they are right now—using the hardcoded .json Service Account file—and use the gcloud CLI independently for your manual and administrative tasks.
The two authentication methods do not conflict with each other. Here is why this works and how they coexist:

🔄 The Separation of Duties
Google Cloud is built to handle multiple identities simultaneously. On your same computer:
• Your Python Script: Acts as a Service Account (an automated robot identity). Every time you run the script, it reads the .json file, talks directly to the Earth Engine API, and performs its code tasks. It doesn't know or care if the CLI is installed.
• Your gcloud CLI Terminal: Acts as You (your human email account). When you open your terminal and run a command (like gcloud storage buckets list), it uses the credentials you gave it via gcloud init or gcloud auth login. It completely ignores your Python script's .json file.

Created a default .boto configuration file at [/home/bruce-vdb/.boto]. See this file and

`.boto` is the configuration file for `gsutil`, the older Cloud Storage command-line tool. The first time you run a `gsutil` command, it creates a default one automatically, and that message is just telling you where it put it. Nothing is wrong.

**What it contains**
- Credentials settings (usually empty at first, since gsutil can use your gcloud login instead)
- Default project ID
- Transfer tuning options such as parallel uploads, chunk sizes, and retry behavior
- Proxy settings, if you need them

**Do you need to edit it?**
Usually not. In most cases gsutil picks up your `gcloud auth login` credentials and the project from `gcloud config`, so the default file works as is. It's only worth editing if you need a proxy, want to set a default project just for gsutil, or want to tune upload/download performance.

**One related tip**
Google now recommends `gcloud storage` over `gsutil` for new work. It's faster and ships with gcloud itself, so it doesn't need a `.boto` file. The commands map closely:

```
gsutil ls gs://my-bucket          ->  gcloud storage ls gs://my-bucket
gsutil cp file gs://my-bucket/    ->  gcloud storage cp file gs://my-bucket/
gsutil rsync -r dir gs://bucket   ->  gcloud storage rsync -r dir gs://bucket
```

If you only use `gcloud storage`, you can ignore the `.boto` file entirely. And if you ever see odd credential errors from gsutil, that file (or a leftover `GOOGLE_APPLICATION_CREDENTIALS` variable) is the first place to look.

move to new directory (from Downloads)
---------------------------------------

Yes, the install is tied to where it was unpacked (`~/Downloads/google-cloud-sdk`), and your PATH entry points there. It works, but if you clean out Downloads, gcloud breaks. The fix is to move it somewhere permanent. Your login and project settings live in `~/.config/gcloud`, so you won't need to re-authenticate.

    **1. Move the SDK**
$ mv ~/Downloads/google-cloud-sdk ~/google-cloud-sdk

    **2. Re-run the installer from the new location**
$ ~/google-cloud-sdk/install.sh

Answer **yes** to updating your PATH and enabling shell completion, and accept the suggested rc file (`~/.bashrc` on Ubuntu).

    **3. Remove the old PATH lines**
The installer from the Downloads folder already added a block to `~/.bashrc`, and it still points to the old path. Find it:

$ grep -n "google-cloud-sdk" ~/.bashrc


You'll see a block like this, with paths containing `Downloads`:
# The next line updates PATH for the Google Cloud SDK.
if [ -f '/home/bruce-vdb/Downloads/google-cloud-sdk/path.bash.inc' ]; then . '...'; fi
# The next line enables shell command completion for gcloud.
if [ -f '/home/bruce-vdb/Downloads/google-cloud-sdk/completion.bash.inc' ]; then . '...'; fi

Open `~/.bashrc` in an editor (`subl ~/.bashrc`) and delete the old block, keeping only the new one that points to `/home/bruce-vdb/google-cloud-sdk/`.

    **4. Reload and verify**
$ source ~/.bashrc
hash -r
which -a gcloud gsutil
gcloud info | grep "Installation Root"

    /home/bruce-vdb/google-cloud-sdk/bin/gcloud
    /home/bruce-vdb/google-cloud-sdk/bin/gsutil
    Installation Root: [/home/bruce-vdb/google-cloud-sdk]

`Installation Root` should now show `/home/bruce-vdb/google-cloud-sdk`, and `which` should list only that location (plus `/usr/bin/gsutil` if you haven't removed the old apt copy yet).

Everything else in your `gcloud info` output looks healthy: the right account and project are active, and gsutil and bq are installed. You can delete the leftover `google-cloud-cli-*.tar.gz` archive in Downloads if it's still there.



Verify Your Active Credentials
-------------------------------
To confirm exactly who the CLI thinks you are and which project it is looking at, run:

<<<bash
gcloud config list
>>>

[core]
account = marron.bruce.mx@gmail.com
disable_usage_reporting = False
project = agremotesensing

Your active configuration is: [default]


This will print out your active user account identity and the active project = your-project-id on your screen. You are now ready to run your administration and bucket management commands safely.


Your active configuration is named **default**, and it holds three settings:

- **account:** `marron.bruce.mx@gmail.com`, the identity gcloud uses for every command
- **project:** `agremotesensing`, so you don't need `--project=agremotesensing` on each command
- **disable_usage_reporting:** `False`, meaning gcloud sends anonymous usage statistics to Google. Set it to `True` if you'd rather not: `gcloud config set disable_usage_reporting true`

The configuration is stored at `~/.config/gcloud/configurations/config_default`, which is outside the SDK folder. That's why moving the SDK won't affect it.

Since you work on one project, `default` is all you need. If you ever juggle several projects or accounts, you can create named configurations and switch between them:

```
gcloud config configurations create other-project
gcloud config configurations list
gcloud config configurations activate default
```

A couple of useful related commands:

```
gcloud config get-value project
gcloud config set project NEW_PROJECT_ID
```

One thing worth knowing: `gcloud config` only affects the gcloud tools. Your Python Earth Engine scripts take their project from `ee.Initialize(project='agremotesensing')`, so set that explicitly in your code.




Display name vs Project ID
--------------------------
Partly. The project **ID** can never be changed, but the **display name** can be changed freely without affecting anything. You keep using the project ID, agremotesensing. The display name is only a label in the console, and gcloud never uses it to identify a project.
    - **Project ID** (`agremotesensing`): permanent. It's what gcloud, Earth Engine (`ee.Initialize(project=...)`), IAM, and API calls use.
    - **Project number**: also permanent, and used internally by Google.
    - **Display name**: a cosmetic label shown in the console. Changing it affects no authentication, IAM bindings, APIs, or your bucket.

**Change the display name**

```
gcloud projects update agremotesensing --name="ag-remote-01"
```


**If you really need a different ID**
The only route is to create a new project and migrate:

    - Register the new project for Earth Engine and enable the APIs again.
    - Re-grant IAM roles and relink billing.
    - Copy your data to a bucket in the new project. Bucket names are global and can't be renamed, so `gcloud storage cp -r gs://ag-remote-bucket01 gs://new-bucket` or `gcloud storage rsync` would be needed.
    - Update `ee.Initialize(project=...)` and your gcloud config in every script.

Since everything is working now, I'd just change the display name if the label bothers you, and keep the ID as is.











Link Your Existing Service Account (Optional)   <== DO NOT USE!!
----------------------------------------------

Since you are using a .json Service Account file for your Earth Engine Python scripts, you can explicitly credential your terminal to act as that service account robot instead of your human email.
To override your human login and authenticate using your file, run:
<<<bash
gcloud auth activate-service-account --key-file="/path/to/your/credentials.json"
>>>

Method 1: Credentialing as a Service Account
• Crippled gcloud Functionality: Many gcloud commands—especially high-level administrative tasks like creating new projects, modifying billing accounts, or managing organization structures—explicitly block service accounts from running them.
• No Audit Trail for Individuals: If three different developers use the exact same service account key to make changes via their terminals, the Cloud Logging logs will only show that the robot did it. You lose visibility into which human operator initiated the action.
