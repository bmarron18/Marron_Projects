I've written the script and tested it in a sandbox with sample files. It compares two `.txt` files symbol by symbol and writes a report with a table of the differences.

To use it:

```bash
chmod +x compare_texts.sh
./compare_texts.sh
```

It picks up the two `.txt` files in `~/Desktop/compare_files` (it stops with an error if there aren't exactly two). It saves the report to `~/Desktop/comparison_made/comparison_<A>_vs_<B>_<timestamp>.txt`, creating both folders if they're missing.

The report has three parts:

1. **Summary:** file sizes, line counts, number of differing symbols and a similarity percentage. If the files are identical, it says so and stops.
2. **Difference table:** lines are paired by number and symbols by column. Each difference gets a row like this:

   ```
   LINE     COL      SYMBOL IN A    SYMBOL IN B
   2        17       f              [SPACE]
   2        20       (none)         x
   5        all      (20 symbols)   (no line)
   ```

   Spaces, tabs and carriage returns are shown as `[SPACE]`, `[TAB]` and `[CR]`.
3. **Line diff:** the standard `diff` output, which lines text up properly when something was inserted or deleted.

The position-by-position table is literal. If a word is inserted early in a line, everything after it shows as different. Section 3 is there to show what actually changed in that case.

On Ubuntu, the default `awk` is `mawk`, which works on bytes rather than characters. The script prefers `gawk` when it's installed (`sudo apt install gawk`) so accented letters count as one symbol. Without it, the script still works, but a character like `é` shows up as two bytes (`[0xC3]` `[0xA9]`).

The table is capped at 5,000 rows to keep the report readable. You can change `MAX_ROWS` at the top of the script.

**How Table 2 works**

Both texts are split into words, and the two word lists are aligned with `diff`, as Table 3 aligns lines. A phrase that was inserted or deleted shows up as one row rather than shifting everything after it. Each row is a block of consecutive differing words. Here's a sample:

```
#   TYPE       LINE A  LINE B  WORDS  TEXT IN A                    TEXT IN B
1   CHANGED    1       1       1/1    brown                        red
2   CHANGED    1       1       1/1    jumps                        leaps
5   ONLY IN B  ~2      2       0/3    -                            mucho frío y
6   ONLY IN A  3       ~2      8/0    This sentence is only in...  -
```

- **TYPE:** `CHANGED` means the wording differs. `ONLY IN A` means the words were removed in B, and `ONLY IN B` means they were added.
- **LINE:** the line number in each text. `~2` marks the spot near line 2 where the other text has no words.
- **WORDS:** how many words are in the block in A and in B. `1/1` is a single word swap, and larger counts are phrases.

Section 1 now reports word counts, the number of difference blocks and a word-level similarity percentage. It still gives the position of the first differing symbol, and Table 3 (the line diff) is unchanged.

**Two optional switches**

By default, `dog.` and `dog!` count as different words, and so do `Fox` and `fox`. For a comparison of word choice only, you can turn that off from the command line:

```bash
IGNORE_CASE=1 IGNORE_PUNCT=1 ./compare_texts_v3.sh
```

`IGNORE_PUNCT` ignores punctuation at the start and end of words. The report header records which options were used. If the files differ only in spacing, case or punctuation, Table 2 says so instead of showing an empty table.

- **gawk vs. mawk:** as before, `gawk` (`sudo apt install gawk`) gives full character handling. With plain `awk`, accented letters still work inside words, but the column alignment can shift slightly on accented text. Yes, there are a few additions that would matter for translations. These are the ones I'd rank highest.

1. **Normalize the text before comparing.** This is the biggest source of false differences. Accented letters can be stored in two ways (é as one character, or e plus a combining accent). Text copied from Word or PDFs also mixes straight and curly quotes, different dashes, non-breaking spaces and hyphenated line breaks. All of these show up as "differences" even though the wording is identical. A short pre-processing step (Unicode NFC via `perl`, plus a few `sed` replacements) would remove that noise.

2. **Context around each difference.** Each row could include a few words before and after, so you can see where the change sits without opening the text. When you're reviewing hundreds of rows, this saves the most time.

3. **Paragraph or sentence numbers instead of line numbers.** If the two translations wrap lines differently, "LINE" is meaningless. Numbering by paragraph (blank-line separated) or by sentence would let you find each difference in either document.

4. **A TSV or CSV export of the table.** Opened in a spreadsheet, it lets you add your own columns, such as "synonym / grammar / omission / mistranslation" and "which is better". The script can only show that *jumps* became *leaps*. It can't tell whether that's a style choice or an error, so the classification has to come from you (or from an LLM, if you pasted the table into a chat).

5. **A flag for risky differences.** Blocks containing digits, dates or capitalized words (names, places) can be marked separately, since a change there is more likely to be an actual mistranslation than a stylistic one.

Lower priority but useful:

- **A vocabulary comparison:** words used by only one translator, and how often each uses common terms ("however" vs. "but"). This shows each translator's habits, such as literal vs. free.
- **Style statistics:** average sentence length, length ratio between the two texts, and vocabulary richness.
- **An inline marked-up version of the text** (`[-old-]{+new+}`, or colored HTML), which reads more naturally than a table.
- **Detection of moved phrases.** A phrase that was reordered currently appears as one removal plus one addition, and translations reorder often.

Are you comparing two translations of the same source into one language, or a source text against its translation? The second case needs different tools, because there is no shared vocabulary to align, so I'd want to know before building any of this. Tell me which of the items you'd like and I'll add them.
