The traceback points to one root cause: `client.files.upload()` is being passed a `pathlib.Path` object as the filename in the `(filename, file, mime_type)` tuple. The underlying `httpx` multipart encoder needs the filename to be a plain `str`, not a `Path` — hence `TypeError: expected string or bytes-like object, got 'PosixPath'`. The same `Path`-where-`str`-is-expected mistake also lurks in the `"title": filename` line when building the `document` content block.

Fixing both spots (using `.name` to get a plain string basename) resolves it.Root cause: `client.files.upload()` (and the `document` block's `title`) were being passed `pathlib.Path` objects where the underlying httpx multipart encoder needs a plain `str`. `Path.__str__` works fine most places, but the multipart filename-header formatter calls a regex `.sub()` directly on the value, which only accepts `str`/`bytes` — a `Path` fails there, producing exactly the traceback you saw.

Fix applied in both spots: use `filename.name` (the basename as a real string) instead of the `Path` object itself, while still using the original `Path` for `open()` and for local bookkeeping/printing. Everything else in the script (model id, content-block structure, cleanup loop) was already correct, so I left it untouched.
